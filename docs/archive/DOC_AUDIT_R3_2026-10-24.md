## 4. 新发现问题

### R1（medium）§0 基线正文与事实不符，靠容忍度通过

`docs/STATUS.md:11` 当前写着：

> `master` 与工作分支 `frontend/ui-audit-p1` **均在** `9be3cbb`（2026-10-24 合流并推送，**单一基线**，未部署）

实测：

```
master               = 8f20f75   （领先 2 个提交）
origin/master        = 8f20f75
frontend/ui-audit-p1 = 9be3cbb
```

`9be3cbb` 是 HEAD 祖先、落后 2 个提交，落在校验器 `≤3` 的容忍窗口内，故通过。但正文使用绝对语气（"均在""单一基线"），与事实不符：master 已前进到 `8f20f75`，两个分支也不再同一基线。

**性质判断**：容忍度本身是必要的——更新 §0 的那个提交必然移动 HEAD，哈希在提交前无法写出，所以容忍度必须 ≥1。问题在**措辞精度与机制容忍度不匹配**：机制允许 3 个提交滞后，正文却写成零滞后的事实陈述。

**建议**：把该块拆成可验证的两句，例如

> 合流基线 `9be3cbb`（2026-10-24 合流并推送）；此后 `140ec78`、`8f20f75` 两个文档/脚本提交未改业务代码。

这样正文永远可被读者直接核对，容忍度无需调整。

### 方法学备注

本轮初次提取 §0 哈希时，因 PowerShell 双引号 here-string 中反引号为转义符，正则的 backtick 被吞掉，导致匹配到 `feedback` 中的 `feedbac`，产生"§0 含 5 个哈希"的假象。改为直接按行读取文件后确认为 **4 个**（`9be3cbb`、`2104167`、`d6335b8`、`c2c38c9`），与校验器输出一致。记录于此以免复现同类误判。

### 复现方法

```powershell
# 契约与文档卫生校验（三目录登记、248 条链接、基线漂移）
.\.contract-venv\Scripts\python.exe -B scripts\validate_contract.py

# 项目自有 md 的全量相对链接检查（排除 vendored 文档与站点绝对路径）
.\.contract-venv\Scripts\python.exe -c @"
import re, pathlib, urllib.parse
root = pathlib.Path('.')
skip = {'.git','node_modules','.contract-venv','target','dist','.cache','temp','.tools','.workbuddy'}
files = [p for p in root.rglob('*.md') if not (set(p.parts) & skip)]
bad = []; total = 0
for p in files:
    for m in re.findall(r'\[[^\]\n]+\]\(([^)\n]+)\)', p.read_text(encoding='utf-8')):
        if re.match(r'^[a-z]+://', m, re.I) or m.startswith(('#','/','mailto:')): continue
        total += 1
        fn = urllib.parse.unquote(m.strip('<>').partition('#')[0])
        if fn and not ((p.parent/fn).resolve().is_file() or (fn.endswith('/') and (p.parent/fn).resolve().is_dir())):
            bad.append(f'{p.as_posix()} -> {m}')
print(f'linking {total}; BROKEN {len(bad)}')
for b in bad: print('  ', b)
"@
```
